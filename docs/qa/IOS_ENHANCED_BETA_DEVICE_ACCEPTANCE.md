# iPhone beta acceptance

Use this alongside the [TestFlight runbook](IOS_STAGING_TESTFLIGHT_RUNBOOK.md) and [release tracker](https://github.com/darshitmeghani1992/the-wall/issues/57). The steps below are prepared for independent QA. Device and hosted results are pending.

## Before the session

- Record the reviewed source SHA, CI run, TestFlight build ID, app version and build number, device model and iOS version, approved environment reference, applied migration versions and active feature flags.
- Use three separate staging identities. A owns the Walls, B is an invited member and approved writer, and C follows A and stays outside the private Shared Wall. Give C access only where a later case calls for it. Use the separately authorized moderator role for moderation.
- Prepare synthetic data: a public Personal Wall, a private Shared Wall, a fresh invite that B can open while signed out, a second invite that B can decline, and a small photo, video and voice fixture. Keep a pending invite for retry tests. Preserve the owner and outsider accounts until the account deletion case has finished.
- Stop a case if its preconditions are absent. Record it as Blocked with the dependency. Use real delivered staging codes for signup and an approved signed build for physical device results.

## Run order

Group cases by account and Wall so QA can reuse the same data. Run B's invite arrival first, while B is signed out. Capture C's first denial before changing relationships. Run block, removal and deletion cases after the normal journeys so the earlier cases keep their fixtures.

| Case | Steps | Expected result |
| --- | --- | --- |
| 1. Installed start and signup | Open a pending Shared Wall invite on a fresh install, sign in as B with a delivered code and finish onboarding. Repeat sign-in with invalid or expired input, resend and a returning session. | Cold start and sign-in show usable states. A valid session restores the exact invite once. Bad input stays recoverable. Reopening after onboarding lands in the expected place. |
| 2. Shared Wall invite recovery | On B's invite screen, induce a temporary network failure on accept or decline. Restore connectivity and tap Retry. Complete acceptance. Use the separate invite to exercise decline. Switch to C and revisit B's saved invite route. | Retry reloads the same invitation after arrival. The completed action resolves once and membership matches it. C cannot read or act on B's invite, including after switching accounts. |
| 3. Walls and permissions | A creates and previews the private Shared Wall, switches between it and the Personal Wall, and shares the permitted destinations. B opens them, receives posting access, posts a text Mark and returns. C follows A and tries to open the private Wall and post on A's Personal Wall before approval. Verify the result after A revokes B's access. | Switching and native sharing land on the intended Wall. A's settings govern visibility and posting. Following grants no posting permission by itself. Revocation applies to a fresh read and a saved link. Closed routes recover to an available destination. |
| 4. Text-first release checkpoint | With the baseline's approved flag set, publish, react to, report and remove a test text Mark. Check the relevant Alerts destinations and an unavailable Mark link. Check logout and account switch. | Text actions persist, pending actions can be retried, and removed items become unavailable. The prior actor's content and pending actions clear on account switch. Gated features follow the baseline's approved flag state. |
| 5. Photo, voice and video | Use the separately approved feature-enabled build and hosted worker. Capture or choose photo and video, deny then allow permissions, record and preview voice, cancel a picker, try discard during an outstanding native action, and retry a failed upload. Verify hosted playback from A and B, then check C and a revoked member. | Drafts stay on the right Wall, canceled pickers produce no attachment, and late native results cannot restore a discarded draft. Photos retain full-frame rendering and swipe order. Voice respects 60 seconds and video respects 30 seconds. Only eligible actors can play private media. Verify expiry, cleanup and the processing result separately. |
| 6. Standard Polls | Create single- and multiple-choice Polls on eligible Personal and Shared Walls using two to six choices. B votes and changes a vote before close. C tries to vote without posting permission. Close as author, then retry a vote. | Valid selections and aggregate results agree across eligible views. Voter names stay private, C cannot vote, and closed polls reject new votes and changes. Secret mode is unavailable in the Poll composer. |
| 7. Anonymous and Secret Marks | Exercise approved Anonymous behavior using the Wall, Alerts and links. With the separate Secret gate approved, exercise first reveal, repeat reveal, removal before reveal, and one-hour expiry with cleanup. | Anonymous identity stays protected. An eligible Secret recipient sees one reveal. Removed, expired and already consumed payloads stay unavailable. Cleanup leaves the expected state. |
| 8. Block, report and deletion | Exercise both sides of block/unblock, report delivery, moderation and unavailable destinations. Use the currently approved Shared Wall exit/removal expectations and record any unresolved behavior against issue #177. With approved deletion infrastructure, test recovery and final deletion, then recheck open and closed Poll totals. | Restricted interactions and stale links close safely. Moderation and deletion have the expected audit, privacy and retention effects. Deleted-account ballots are removed from open and closed Polls. |
| 9. Accessibility and stability | Repeat key journeys with VoiceOver and larger text. Capture cold launch, Wall paint, media progress, background/resume, interruption recovery and crashes against agreed targets. | Controls have useful labels and focus order, text remains usable, and the app recovers from interruptions. Record measurements against the established release targets. |

Cases 1–4 cover the controlled baseline when their preconditions are met. Repeat them with the feature-enabled candidate before external distribution and add cases 5–9. For hosted permission cases, pair the device results with separate owner/member/outsider API and database checks in approved staging.
