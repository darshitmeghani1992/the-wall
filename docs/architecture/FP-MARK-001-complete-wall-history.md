# Feature Plan: Complete Wall Mark History

**Status:** Proposed, not build-ready pending Product/Founder approval and architecture review
**Product input:** `docs/product/PRD-MARK-001-complete-wall-history.md`
**Tier:** Medium; client read and navigation contract, three Wall screens
**Complexity estimate:** Several focused Frontend sessions plus independent Reviewer and device QA
**Reversibility:** Client-only design is reversible before release. No migration proposed.

## Repository evidence

- `src/lib/marks.ts` reads all active rows for a Wall with `pinned DESC, created_at DESC`, with no cursor, tie-breaker, or page limit.
- `src/lib/deferred-destination-resolver.ts` receives `wallMarks(wallId)` and treats absence from that array as terminal. All three Wall screens pass their full-list promise and focus by searching its result.
- `src/lib/created-at-pagination.ts` already validates semantic timestamps and UUIDs for raw PostgREST cursor expressions. Alerts uses a 50+1 lookahead with an ID tie-breaker.
- `Masonry` lays out the supplied array in memory. Reactions and realtime arrivals currently operate over that loaded array.
- The initial schema has `marks_wall_created_idx` on `(wall_id, created_at DESC)`; it lacks a pinned-first composite index. Query plans and actual hosted table sizes have not been measured.

## Proposed read contract

1. Introduce `listWallMarks(wallId, cursor?)` with a fixed 50+1 lookahead, stable `(pinned DESC, created_at DESC, id DESC)` order, active status, Wall ID filter, and existing RLS. The cursor captures all three sort keys. Validate UUID, timestamp, and boolean before composing any PostgREST expression. Return hydrated visible items plus a cursor only when lookahead proves another page.
2. Add a separate `getWallMark(wallId, markId)` exact read with `wall_id`, `id`, and `status=active` predicates under existing RLS. A typed null means terminal unavailability; query or hydration failures throw and remain retryable. The deferred resolver accepts an exact-Mark operation instead of checking membership in a list.
3. On each Wall screen, fetch the first page and the exact target independently when `focusMark` exists. Select the target from the exact read even when it lies outside loaded history; avoid duplicating it in the Wall grid if a later page includes it. Fence requests to the current account, Wall, navigation target, and refresh generation. Append pages by unique ID, retaining the cursor after a failed load.
4. Keep live inserts visible once. Reload the first page after a pin, removal, or other sort-changing mutation rather than claiming a stale cursor is a complete snapshot. Filter only the loaded list; the older-page action remains available even when the filter has no loaded matches.
5. Display a separate exact active-Mark count or label the displayed number as loaded. A count read must use the same Wall/status/RLS boundary and show an unavailable state on error instead of reporting a partial count as the total.

## Design questions before build

- Confirm with Product whether the header should show an exact total or an explicit loaded count, and the desired older-history action copy.
- Confirm a PostgREST expression for the pinned boundary against a real or local Supabase instance. Avoid assuming that a nested `or` generated by the client composes as intended.
- Measure `EXPLAIN` and actual data volume before deciding whether a new index is needed. A migration would be a separate Founder gate and independent architecture review.
- Check whether sorting of realtime insertions and pin actions already follows pinned-first order; include correction in the approved implementation scope if needed.

## Verification and handoff

Pure cursor and append tests should cover malformed values, equal timestamps, pinned boundary, duplicates, and reordered live arrivals. Source/integration tests should cover exact read rather than list membership, each Wall's account/navigation fence, partial-count copy, filtering, and retry. Device QA must cover older exact links, authorization outcomes, page failures, and long Personal/Shared Walls. Reviewer inspects the exact tree and RLS-preserving query shapes. No hosted state, merge, or deployment is part of this proposal.

**Build readiness:** NOT READY. Product-facing choices and the predicate/index evidence above remain open; no engineering Role should interpret this plan as authorization to implement a new UI or schema.
