# Poll storage isolation from the legacy Mark stream

Status: proposed architecture for review. Release candidate [#228](https://github.com/darshitmeghani1992/the-wall/pull/228) at `6818a581a69a8f95494e6f8a8f67d85753a7b462`. Keep the server creation and voting gates, the app composer and the focused reader off. No changes to publication, replica identity, app, database or hosting are authorized by this document.

## Decision and source evidence

**Recommend a Poll parent that is physically outside all client-facing publications.** Keep the current `public.marks` table, its publication membership, replica identity, v1 raw RLS and subscription behavior unchanged. Serve Poll cards exclusively from actor-bound v2 reads. Do not use a shadow/tombstone Poll Mark in `public.marks`.

- At #228, `0001_init.sql` adds `marks`, reactions and notifications to `supabase_realtime`. `0019_disable_excluded_surfaces.sql` removes comments. Poll draft migrations 0035/0036 still place the Poll parent in `marks`; they do not change the publication. `src/lib/marks.ts` maintains raw SELECT for legacy history/detail and an INSERT-only Wall subscription. The callback is not a server-side privacy boundary. The new v2 reader and suppression of old Mark-left alerts cannot prove DELETE isolation.
- Supabase documents that Postgres Changes DELETE is not RLS-filtered. For the public upstream PostgreSQL 17 tenant snapshot reviewed, the Realtime poller calls `list_changes` and that SQL selects publication event kinds and table names, then passes `add-tables` to the wal2json decoder. It does not consume a publication row predicate. PostgreSQL's built-in logical replication row filters, which constrain UPDATE/DELETE replica identity, are therefore insufficient evidence for this Realtime adapter. Hosted target behavior was not queried or tested. Do not assume that a WHERE clause, changing replica identity, SELECT RLS or changing the app callback protects the old event stream. [Supabase DELETE behavior](https://supabase.com/kb/troubleshooting/realtime-messages-not-arriving) · [Upstream PG17 list_changes](https://github.com/supabase/realtime/blob/177d6e841cc9e1c84a2ea9acf6780ac16459dac0/priv/repo/tenant_db_dump_17.sql#L849) · [PostgreSQL row filters](https://www.postgresql.org/docs/17/logical-replication-row-filter.html)
- At #228, migration 0027 defines the SECURITY INVOKER `remove_mark`. Its existing raw Mark RLS path cannot see a Poll parent. The existing report and Alert foreign keys in 0001 also point to `marks`. Do not broaden raw Mark selection, fake a parent, or add a generic Poll Alert. Poll moderation and reports need an explicit authorized target path.
- Migration 0031 explicitly removes authored canonical Marks and then the deletion worker calls Auth Admin identity removal. Draft 0036 cascades ballots for that identity. Rebinding either deletion phase must preserve the already approved loss of that voter's contribution to totals, even for closed polls, and must not emit a legacy Mark event. No hosted deletion or event reproduction was performed.

## Proposed contract and implementation order

1. **Separate storage.** Put Poll parent identity, exact Wall, actor, status, pin and created time in a dedicated private relation or the existing private Poll definition after redeveloping the unapplied drafts. Give it no API-client table access and no membership in client publications, including schema-wide and all-table publications. Put options, ballots, selections and mutation receipts behind actor-bound RPCs. Use explicit composite Wall/Poll keys and cascades within this private hierarchy. Keep app-facing Mark ACLs and existing text/media table, topic and subscription behavior as-is. Leave legacy `poll_votes` and historical rows closed. Verify the parent never enters `public.marks`; a Poll cannot be represented by a normal Mark row.
2. **Read and route.** Have v2 Wall history union the existing authorized ordinary Mark rows with authorized active Poll parents using one mixed keyset. Carry the kind in the cursor tie-break and bind focused Wall/ID/kind so equally ordered or coincident IDs cannot return the wrong resource. Gate both arms on current actor and Wall authorization; return the viewer's own Poll ballot and aggregate counts only. The existing raw history/detail paths and legacy listeners never see a Poll. The current Poll-aware client gate stays closed until updated to the reviewed v2 contract. No Poll Realtime or new Alert topic is required for first activation; authorized v2 refresh is sufficient.
3. **Lifecycle and moderation.** Create an actor-bound Poll report/remove capability against the dedicated Poll identity. Reuse the same owner, accepted member, admin and active-account rules where applicable. Reuse or deliberately coordinate the existing Mark removal quota and concurrency mechanism across ordinary Marks and Polls so the new path cannot bypass limits. Keep audit target type explicit, private and attributable without exposing the author/voters. Preserve existing report and Mark routines and their foreign keys. If a Poll report needs a new FK or moderation queue item type, forward a reviewed typed target to that work. Do not expand invocation privileges of generic APIs.
4. **Delete safely.** Wall deletion cascades its private Poll hierarchy. During separately approved account purge, remove authored Poll parents and all of the purged identity's ballots and receipts under the documented account lifecycle. Use exact ownership-linked FKs and deterministic locks to keep cancellation and retries safe. Protect inactive actors immediately using read/write predicates. On an authorized closed-Poll read, derive totals from remaining ballots; do not retain a pre-purge snapshot. If Auth removal is the final cascade, test interruption between purge preparation and Auth removal and verify after both phases. Do not alter existing text/media, Anonymous Mark or Secret cleanup behavior.
5. **Adopt through separate review.** No draft migrations have been applied to hosted environments. Prefer a single reviewed no-write migration path from the actual installed baseline, with gates still off. Any disposable fixtures already on the old draft schema need an explicit reset or conversion test. Require Founder architecture/runtime approval and independent Reviewer/QA before changing either environment.

## Draft implementation on the pre-Poll baseline

The draft rewrites the unapplied 0035 and 0036 migrations. `public.mark_polls` owns the Poll ID, Wall, author and status. The options, ballots and receipts reference it. The migrations abort if an effective publication contains a private Poll relation. Neither migration changes the ordinary Mark table, its publication membership, the legacy retired-kind rules or generic moderation and deletion functions.

- The create RPC keeps its existing request and receipt. The bounded batch reader returns only the authorized Poll projection. The existing untyped focused RPC rejects an ambiguous ID when both resources are readable.
- `get_wall_mark_item_v2` adds exact `p_kind` selection for new clients, with `mark` or `poll` and no fallback to the other kind. `list_wall_marks_v2` accepts the full `p_after_pinned`, `p_after_created_at`, `p_after_mark_id`, `p_after_kind` cursor or four nulls. The returned cursor adds `kind`. The sort is descending by pin, time, ID and then kind, and a Poll is distinguishable from an ordinary Mark even when the other three keys tie.
- Vote replacement and author close lock the same private parent and recheck current actor, Wall and block authorization. Auth identity removal subtracts the synthetic voter's ballot from closed totals in disposable tests. The account purge prepare/finalize flow and Poll-aware moderation still require their own review before activation.
- Both server write gates and the app gates remain off. Test suites 82–84 cover private storage, typed focus, pagination, vote/close, Auth cascade and concurrent authorization. The suite snapshots the ordinary Mark catalog before and after both migrations. Environments holding the old drafts require a separate reset or conversion plan.
