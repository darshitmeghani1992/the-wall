# ADR-012: Private, staged, server-validated Mark media

**Status:** Accepted — worker-credential amendment independently Two-Key approved 2026-09-03
**Date:** 2026-08-27
**Fast Lane:** High-Risk / Architectural
**Supersedes:** ADR-006 and D-6 **for Mark media only**. The public `attachments` bucket remains authoritative for public avatars.

## Context

The current client uploads one photo, voice clip, or video to the public `attachments/marks/*`
prefix and writes a permanent URL into `marks.media_url`. Migration `0018` correctly stops
that path: authenticated clients can currently create text Marks only, new Mark-object uploads
are denied, and media fields fail closed. Package C must restore Photo/Voice/Video Marks without
reopening public media or trusting client-supplied MIME, size, dimensions, duration, path, author,
Wall, or ordering.

The approved product contract is fixed:

- canonical Mark types are `text`, `photo`, `voice`, and `video`;
- Photo supports 1–5 ordered images and preserves the complete frame rather than cropping it;
- Voice is at most 60 seconds; Video is at most 30 seconds;
- Secret media remains rejected until a separate one-time media-access design is approved;
- a failed multi-file post creates no partial Mark, media relation, or Alert.

This is personal-data infrastructure: users may place photos, voices, and videos on private
Personal or Shared Walls. Access, metadata removal, blocking, retention, and legacy public URLs
therefore have privacy consequences and require independent Security/QA verification.

## Decision

### 1. Private bucket and two-phase lifecycle

Create a private `mark-media` bucket. Uploads first enter an untrusted staging path generated by
the server:

The bucket `file_size_limit` is exactly **52,428,800 bytes (50 MiB)** so canonical Video output may
reach its 50 MiB cap. This coarse bucket ceiling does not widen input acceptance: Video reservation,
upload transition, and trusted processor input validation remain capped at exactly **41,943,040
bytes (40 MiB)**.

`staging/{auth.uid()}/{media_upload_id}/source`

The client cannot choose a bucket path and cannot upload unless an unexpired `media_uploads` row
for the exact path, Wall, user, and kind already exists. Photo, Voice, and Video never become
Mark-readable from staging. A trusted processor validates the object and writes an attempt-scoped
canonical output:

`validated/{media_upload_id}/{processing_attempt_id}/full.{server_extension}`

Photo may additionally have an aspect-preserving thumbnail at `.../thumb.webp`; Video may have a
poster at `.../poster.webp`. Only the current successful attempt becomes `validated`. Staging and
superseded-attempt objects are cleanup-only and never receive app read access.

The bucket is private because Supabase states that private-bucket downloads are subject to RLS or
must use time-limited signed URLs, while public buckets bypass retrieval access control. See
[Storage Buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and
[Serving assets from Storage](https://supabase.com/docs/guides/storage/serving/downloads).

### 2. Durable database state is the workflow authority

`media_uploads` is both the upload authorization record and the durable job state machine. It is
not a client-maintained progress log. The server owns state transitions:

`initiated → uploaded → processing → validated → consumed`

Terminal/non-happy states are `failed` and `expired`. A lease and attempt identifier make worker
retries safe. Each processing attempt writes to a unique output path; a late worker can neither
overwrite nor complete a newer attempt. The source remains available until a successful
completion is committed, after which cleanup removes it.

`mark_media` is the immutable, ordered relation from one Mark to its validated objects. It stores
only server-trusted metadata and paths—never a signed URL. App roles cannot read paths or execute
the path resolver. A JWT-verifying Edge signing route calls a service-role-only resolver after it
binds the request to the verified user. Signed URLs are ephemeral bearer credentials and must not
be persisted, logged, emitted to analytics, published over Realtime, placed in referrers, or sent
to crash reporting.

### 3. Direct authenticated uploads; signed, short-lived reads

Uploads use the user's JWT against the private bucket so Storage RLS is evaluated at upload time.
The app uses standard uploads for Photo (hard limit 6 MB) and resumable TUS uploads for larger
Voice/Video objects or unreliable networks. Supabase recommends standard uploads for files no
larger than 6 MB and TUS for larger files or when progress/resume matters. See
[Standard Uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads) and
[Resumable Uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads).

We do **not** use signed upload URLs for the ordinary client flow. Supabase's signed upload URLs
are bearer credentials valid for two hours and can be used without further authentication; that
is a wider post-authorization write window than this product needs. See
[createSignedUploadUrl](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl).
The internal processor may receive a signed destination URL because it is never exposed to an app,
is scoped to one attempt-specific path, cannot complete without the matching database lease, and is
deleted as stale if that attempt loses its lease.

Authorized viewers call the `mark-media` Edge route with their JWT. The deployed function keeps
Supabase's default `verify_jwt=true`, uses the current authenticated-user verification pattern, and
rejects missing/invalid JWTs before privileged work. It passes the verified subject—not a client
actor parameter—to service-role-only `resolve_mark_media_for_signing`. `PUBLIC`, `anon`, and
`authenticated` have no execute grant on that resolver, so direct Data API path resolution is
denied. The route signs only exact returned paths, suppresses paths, and makes missing,
inaccessible, blocked, and deleted Marks externally indistinguishable.

The signed URL lifetime is **60 seconds**. Every canonical object is uploaded with
`cacheControl=60`; completion performs an authenticated HEAD, rejects effective `max-age>60`, and
persists the verified value. The resolver refuses objects without that proof. The Edge JSON
response sends `Cache-Control: private, no-store`, `Pragma: no-cache`,
`Referrer-Policy: no-referrer`, and `X-Content-Type-Options: nosniff`. A hosted test signs and fetches
each kind and proves the object response has effective cache max-age no greater than 60 seconds.
The conservative access-revocation window is approximately 120 seconds: a URL issued just before
authorization changes may remain valid for 60 seconds and a response fetched near expiry may
remain in private browser cache for no more than another 60 seconds.
See [createSignedUrls](https://supabase.com/docs/reference/javascript/file-buckets-createsignedurls)
and [Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

The resolver is the authorization linearization point. In one transaction it locks the Mark and
Wall `FOR SHARE`, takes the existing deterministic pair lock where blocking can change visibility,
locks relevant membership/relationship rows, then evaluates the canonical Mark-read rule. A
revocation committed before that point denies signing; one committed after it has only the bounded
window above. A committed deletion blocks every resolver call whose linearization point follows the
deletion, but a request already resolved or signing in flight may still produce/use a URL for the
same bounded signed/cache window until the asynchronous outbox removes the object and CDN state.
Canonical paths remain immutable; the design does not falsely promise an immediate dead URL.
Signing is actor-rate-limited and returns at most five objects.

Immediate pair-specific revocation cannot be guaranteed for a previously issued bearer URL without
deleting the shared object, which would also break access for other legitimate Wall viewers. The
accepted design is short TTL + short cache + reauthorization on every refresh/re-sign. Object
deletion is reserved for Mark/account retention events, not blocking one viewer.

### 4. A portable isolated processor, not CPU-heavy Supabase Edge code

A containerized `media-processor` is the trust boundary for decoding and re-encoding. Supabase Edge
Functions remain the authenticated orchestration boundary: they claim durable jobs, generate exact
source/destination credentials, and accept attempt-bound completion. They do not decode media.

This separation is required by current hosted Edge limits: 256 MB memory, 2 seconds CPU per
request, and no multithreaded Node libraries such as `sharp`/`libvips`. See
[Edge Function limits](https://supabase.com/docs/guides/functions/limits). Edge background work is
also bounded by the same runtime limits, so `EdgeRuntime.waitUntil` is not a durable media-worker
substitute; see [Background Tasks](https://supabase.com/docs/guides/functions/background-tasks).

The processor is built as an OCI image so the hosting target can change without changing the DB,
client, or Storage contracts. It receives one attempt-scoped job, downloads only the signed source,
writes only the signed destinations, and completes only with the matching opaque completion token.
It never receives a Supabase secret/service key or direct database credentials.

Each dispatch is an Ed25519 compact JWS (`alg=EdDSA`) produced with native Web Crypto. The Edge
orchestrator alone holds the private key; the worker receives only the keyed public-key allow-list,
so compromise of a worker cannot mint or alter a dispatch. The protected header, canonical payload,
key lifecycle, exact URL/path binding, and deterministic test vector are specified once in
[FP-MEDIA-001](./FP-MEDIA-001-protected-mark-media.md#binding-worker-credential-protocol-v2).
The signed dispatch contains a random one-use dispatch nonce and a different random opaque
completion token. The worker verifies the JWS and atomically redeems the dispatch nonce through the
worker Edge gateway before downloading bytes. Completion/failure authenticates to that gateway and
uses one atomic database operation that validates the result, consumes the completion token,
changes attempt state, and writes a durable idempotency receipt.

User media reads and worker callbacks are separate deployments. `mark-media` retains
`verify_jwt=true`; `mark-media-worker` uses `verify_jwt=false` because its dedicated worker bearer
credential is not a Supabase JWT. The worker route performs constant-time custom authentication
before parsing a job token or constructing any privileged client.

Supabase signed upload credentials are conservatively treated as write-capable for two hours.
After every signed destination URL has been returned, Edge records a non-shrinking output-credential
fence equal to that return time plus two hours and 30 seconds. No job may be dispatched before that
fence is durably bound to its attempt. Attempt-output cleanup, deletion evidence, and quota release
must wait until the persisted fence; the shorter five-minute lease or two-minute dispatch envelope
must never be used as the output deletion fence. This prevents a still-valid signed PUT from
resurrecting an object after cleanup was declared complete.

Normal key rotation stops new binding to the retiring key and retains its public key only through
the greatest issued dispatch expiry, never more than 120 seconds after the final issue. A private
database key-state row remains through the greatest bound completion lease so already-redeemed work
can finish. Bind, redeem, finalize, rotation, and emergency revocation all lock and evaluate that
key-state row in the same database transaction as their attempt mutation; environment allow-lists
are defense in depth, not the revocation authority.

The worker accepts HTTPS port 443 only, with no userinfo/fragment, on the exact configured Supabase
project host, bucket `mark-media`, and envelope-bound decoded paths. It rejects IP literals,
private/reserved addresses, alternate hosts, path ambiguity, and all redirects; egress allows only
that Storage origin and Edge callback. It runs non-root with read-only root filesystem, all
capabilities dropped, `no-new-privileges`/seccomp, per-job isolation, bounded tmpfs (512 MiB), 64
PIDs, 1 GiB memory, 2 CPUs, wall clocks of 30/45/120 seconds (Photo/Voice/Video), and output caps of
10/10/50 MiB plus 2 MiB preview. Decoders are pinned/patched with SBOM and CVE gating.

Photo processing must:

- cap source at 6 MB, 8,192 pixels per edge, and 25 megapixels before full decode allocation;
- verify magic bytes, fully decode, and reject malformed, truncated, polyglot, animated, and
  decompression-bomb input;
- normalize orientation and color space; strip EXIF/GPS/comments/thumbnails/private metadata;
- preserve the complete image frame with no forced crop and no upscale;
- emit an immutable sRGB JPEG for opaque input or WebP for required alpha, plus an optional
  aspect-preserving thumbnail;
- compute trusted format, dimensions, byte count, and SHA-256 over each canonical output;
- fail closed on HEIC or another format unless the pinned decoder version demonstrably supports it.

Voice/Video processing must use a trusted parser (`ffprobe`) and canonical output (`ffmpeg`) rather
than client metadata. Voice becomes audio-only AAC/M4A with metadata removed and must be `<=60000`
ms. Video becomes H.264/AAC MP4 with metadata removed, fast-start enabled, no unexpected streams,
and must be `<=30000` ms. AV probing is bounded to 10 MiB and five seconds (or pinned equivalent):
Video is at most 3840x2160, 60 fps, and 1,800 frames with one video and at most one audio stream;
Voice has exactly one audio stream; all audio is at most two channels/48 kHz. Subtitle, data,
attachment, unknown-duration, and conflicting-duration inputs fail closed. Exact codec/quality
presets are implementation constants with golden-file device QA; changing accepted formats or
duration is a contract change.

### 5. One atomic Mark creation contract

`create_mark(...)` is the sole canonical creation path after migration `0022`. It derives the actor
from `auth.uid()`, rechecks account and current contribution authorization, validates the complete
request, locks every referenced upload row, and commits the following in one PostgreSQL transaction:

1. idempotency record;
2. canonical `marks` row;
3. 0, 1, or 1–5 ordered `mark_media` rows;
4. transition of each upload from `validated` to `consumed`;
5. existing Anonymous provenance, Secret-text extraction, and Alert triggers.

Any exception rolls back all five. Text supports no upload IDs. Photo requires 1–5 validated photo
uploads. Voice/Video require exactly one matching validated upload. Media + `secret=true` is rejected.
Legacy `marks.media_url` and `marks.payload` are always null for new rows. Duration, dimensions,
format, paths, and ordering come from locked server rows, never client JSON.

The RPC accepts a client-generated `request_id` and stores a versioned SHA-256 fingerprint over
canonical server-normalized meaningful input: version, Wall, type, exactly inserted normalized
text, color, Anonymous/Secret flags, and ordered upload IDs. Rotation is server-derived and
excluded. A deterministic actor/request advisory lock precedes insert/read; conflicts are row
locked. Same-input pending calls wait and re-evaluate, completed calls return the existing result,
mismatched version/hash fails, and a post-delete tombstone returns `deleted` without recreating.
The request row, Mark, media, upload consumption, provenance, and Alert share one transaction, so a
failure rolls back even the pending request. Uploads are locked in UUID order.

### 6. Default-off controls, atomic quota, and durable deletion

`media_kind_controls` has one private row per Photo/Voice/Video with independent reservation,
upload-transition, processing, and creation switches, all default false. Server functions enforce
them respectively at `begin_media_upload`, upload transition, worker claim, and `create_mark`; a
client flag or direct RPC cannot bypass them. Creation cannot be enabled until legacy
reconciliation is complete. Rollback disables creation first, then processing, transition, and
reservation; only afterward may the client hide the feature.

Reservation uses an atomic per-user/day quota ledger. Under deterministic user/day advisory and row
locks it charges declared bytes, reservation count, and one open upload/TUS session before creating
the reservation. Transition reconciles trusted actual Storage bytes; an over-limit object fails and
is queued for deletion while actual bytes remain charged. An incomplete TUS session holds its
declared charge/open-session slot for the documented maximum 24-hour URL lifetime. Concurrent
reservations cannot cross thresholds.

Object deletion is API work backed by a durable outbox. Before `mark_media` cascade or staging/
account cleanup removes a relation, a trigger enqueues exact bucket, canonical/preview paths,
reason, state, attempt, and deletion evidence in the same transaction. A worker deletes exact paths
(never wildcard), treats not-found as idempotent success, performs a fresh missing proof, and
retains evidence. User/Wall/Mark tombstone IDs survive nullable `ON DELETE SET NULL` workflow FKs;
request tombstones make delayed retries safe.

### 7. Additive cutover and no privacy rollback

Migration `0020_mark_media_foundation.sql` is additive. It creates the private bucket, tables,
constraints, policies, default-off controls, staging/processing contracts, deletion outbox, quota
ledger, reconciliation gate, and `create_mark` but does not yet revoke the migration-0018 text
compatibility insert. A migrated client uses the RPC for all four types and dual-reads `mark_media`
before legacy `media_url`. New policies use `storage.objects.owner_id`; a source transition rejects
null/service ownership and requires exact equality with the uploader JWT subject. Supabase has
deprecated `owner`, and service-key-created objects have no owner. See
[Storage ownership](https://supabase.com/docs/guides/storage/security/ownership).

Migration `0021_media_worker_credentials.sql` additively corrects the worker-credential protocol
using the approved contract in FP-MEDIA-001; it does not perform the Mark-creation cutover. Only
after hosted staging, a reconciled `media_legacy_reconciliation` singleton, processor verification,
client minimum-version enforcement, and adversarial tests pass does
`0022_mark_creation_cutover.sql`; the migration aborts if that gate is incomplete. A legacy worker
may process inventory while user reservation/upload/create switches remain off. Public media
creation cannot be enabled before reconciliation. Reconciliation requires a fresh unauthenticated
denial proof for **every** inventoried legacy URL, including quarantined or missing-source entries;
any reachable quarantine blocks creation, `0022`, and the privacy claim unless the Founder
separately accepts a documented residual privacy exception. `0022` then:

- revoke direct authenticated `INSERT` on `marks`;
- revoke all app writes on `mark_media`, job/ledger tables, and legacy Mark Storage paths;
- make `create_mark` the only runtime creation path;
- enforce null legacy `media_url`/`payload` for every new canonical Mark.

Rollback disables media creation and restores the last known-good client. It does not make the
private bucket public, restore public Mark upload policies, repopulate public URLs, or weaken the
new read boundary. Schema rollback, if ever needed, is a new forward migration after data inventory.

## Consequences

### Positive

- Private Wall media no longer depends on unguessable public URLs.
- Multi-photo ordering and cardinality are first-class and server-enforced.
- Malicious file labels cannot bypass decode/duration checks.
- Network retries cannot duplicate Marks, consume uploads twice, or emit duplicate Alerts.
- The processor can move between infrastructure providers without changing app contracts.
- Public avatars remain simple and cache-friendly in the existing bucket.

### Costs and trade-offs

- A small container worker and scheduled dispatcher are new infrastructure and operating cost.
- Media posting is asynchronous: the user uploads, waits for validation, then posts. The composer
  must preserve its draft and show per-item validation/retry state.
- Signed read URLs deliberately have a bounded revocation lag; immediate pair-specific invalidation
  is not achievable with shared bearer URLs without proxying every byte.
- Photos are preserved visually, not byte-for-byte: the untrusted original is deleted after a safe,
  full-frame derivative is committed.
- Voice/Video remain feature-flagged off until the processor passes real-device and hostile-fixture
  verification; `0020` alone does not make media production-ready.

## Alternatives considered

### Keep public URLs with unguessable paths

Rejected. Public bucket retrieval bypasses RLS, so knowing or leaking a URL defeats Wall access
changes and blocking.

### Put decoding/transcoding directly in a Supabase Edge Function

Rejected for the trusted processor. Current CPU/memory/library constraints are not compatible with
reliably decoding adversarial 25-megapixel images or transcoding video.

### Store client metadata and validate only MIME/size in PostgreSQL

Rejected. MIME, filename, extension, dimensions, and duration are attacker-controlled until a
trusted decoder/parser verifies the bytes.

### Generate two-hour signed upload URLs

Rejected for ordinary clients. They remain unauthenticated bearer write credentials after initial
authorization. Direct JWT uploads let Storage RLS evaluate the current staging row at upload time.

### Proxy every media read through an Edge Function

Deferred. It can provide immediate per-request revocation but adds egress, latency, range-request,
and streaming complexity. The approved MVP accepts the documented short signed-URL window.

## Reversibility

The schema and client cutover are two-way doors until `0022`. After public originals are deleted,
the privacy direction is intentionally one-way: rollback may disable the feature, but may not
republish content. The OCI processor hosting provider remains replaceable.

## Calibrated confidence

- **Verified:** Current repository behavior, migration `0018` cutover state, client single-media
  shape, public bucket behavior, and current official Supabase Storage/Edge constraints.
- **Believed-likely:** The staged state machine and isolated processor are the smallest design that
  meets the approved safety contract without pushing CPU-heavy work into Edge Functions.
- **Inferred:** Hosted legacy object count, active Supabase plan/CDN purge availability, chosen OCI
  runtime, and real-world processor throughput remain unknown until deployment discovery.
