# Standard Poll Mark persistence and API contract

Status: Architect proposal for implementation review. [Founder-approved scope and Product acceptance](../product/PRD-MARK-002-poll-marks.md) require standard single-choice and multiple-choice polls on eligible Personal and Shared Walls. Secret polls and retired game types are outside this beta. This specifies a proposed interface and migration sequence. UI behavior and schema/authorization still need their separate approvals.

Source reviewed: integrated draft [#216](https://github.com/darshitmeghani1992/the-wall/pull/216) at `3a62a2967fe609ef6ab57320ec214e5e3fc4734a`, including the exact [#214 Product/Architect plan](https://github.com/darshitmeghani1992/the-wall/pull/214) and [#215 reporting recovery](https://github.com/darshitmeghani1992/the-wall/pull/215). [Delivery plan](FP-MARK-002-poll-marks.md)

## Existing interfaces and constraints

| Existing implementation | Consequence for this contract |
|---|---|
| `0001_init.sql` and `0019_disable_excluded_surfaces.sql` | The legacy enum contains `poll`; the old `poll_votes(mark_id, user_id, option_index)` supports one index and runtime access is revoked. Never use it for new selections, restore its policies or import historical votes implicitly. |
| `0018_p0_authorization_contract.sql` | Reuse active-account and Wall view/contribution predicates, true Anonymous author lookup, the pair-lock mechanism and canonical Mark moderation. Arbitrary-actor helpers remain ungranted to clients. Existing raw Mark SELECT allowlist excludes polls and remains unchanged. A separate versioned RPC can return only sidecar-backed eligible polls. |
| `0023_mark_writer_contract.sql` and `0024_mark_creation_cutover.sql` | `create_mark` whitelists four types and makes retries actor/request scoped. Keep that signature and whitelist. Keep generic direct INSERT revoked and do not store poll content in `marks.payload`, `media_url` or `text`. |
| `0026_shared_wall_lifecycle.sql` and `0027_actor_bound_safety_mutations.sql` | Membership/state are server-owned and may change while a screen is open. Require an expected actor and re-evaluate privileges after the relevant locks, as existing actor-bound operations do. |
| `src/lib/marks.ts` and `app/create.tsx` | Wall history and detail query raw marks under RLS. Leave that route and its event stream intact for existing clients. Poll-aware builds switch to a versioned, explicitly typed history/detail RPC and can batch-refresh authorized poll data. Do not attempt to discover polls from the old Mark query. Compose through a dedicated frontend service after scope and UX approval. |

## Proposed persistence

| Relation | Keys and invariants |
|---|---|
| `mark_polls` | `mark_id uuid` primary key, `wall_id uuid`, `question text`, `selection_mode text` constrained to `single` or `multiple`, `revision bigint` starting at 1, nullable `closed_at timestamptz`. Composite foreign key to `marks(id,wall_id)`, deletion cascade, initially deferred. Install the matching unique parent key before the foreign key. The parent must use legacy enum value `poll` and have `secret=false` and null generic content fields. Only a private definition paired in the validated creation transaction is canonical. |
| `mark_poll_options` | Primary key `(mark_id,option_id)`, immutable in-scope UUIDs, zero-based unique `position` for a poll, nonempty `label` and server-derived `normalized_label`, unique per poll. Foreign key to definition, deletion cascade. Array order is preserved on creation; approved edits explicitly specify new order and labels. |
| `mark_poll_ballots` | Primary key `(mark_id,voter_id)`, foreign keys to private definition and Auth identity, deletion cascade, positive `revision`. No client-supplied voter ID. Zero represents no ballot and is never stored. Keep no plaintext identity in results or runtime logs. |
| `mark_poll_ballot_choices` | Primary key `(mark_id,voter_id,option_id)`; composite foreign keys to the ballot and that poll's option. A transaction replaces the complete set. Foreign keys constrain poll membership. Deferred constraint triggers, not a cross-table CHECK, protect nonempty ballots and selection cardinality. |
| `mark_poll_requests` | Primary key `(actor_id,request_id)`, Auth identity cascade, operation and canonical versioned fingerprint, target IDs, applied revision and recorded success state. Fingerprint covers the exact action and scope; choice sets are canonicalized without permitting duplicates. A deleted target returns unavailable before any retry payload. Set a reviewed retention horizon before rollout. |

Use the existing `poll` enum without a broad allowlist change. Keep migration 0019's existing invoker trigger and its role-sensitive checks for `anon`, `authenticated`, and `service_role` unchanged. That trigger is not sufficient protection for a caller using a SECURITY DEFINER path or an owner operating directly. Maintain the generic create_mark and direct INSERT denials. Add independent, role-agnostic poll invariants in a new migration. Do not use a cross-table CHECK or an actor-writable setting as a bypass.

1. A definition BEFORE INSERT trigger rejects any existing parent Mark ID, including any legacy `poll`; only the dedicated create RPC can allocate a new UUID and insert the private definition first. A new poll Mark BEFORE INSERT trigger requires that definition to exist with the same Wall, `secret=false`, and null `text`, `media_url`, and `payload`. Those checks apply irrespective of the invoking role. No backfill or promotion of historical poll rows is part of this release. The generic create RPC still rejects all retired types. New poll creation does not alter the historical meaning of other enum values.
2. The composite cascading initially-deferred FK rejects a definition without its parent or a mismatched Wall at commit. Add deferred constraint triggers to enforce the reciprocal invariant after changes to either table: a surviving newly inserted or previously registered poll parent must have its matching definition, and a surviving definition must point to a standard canonical poll. This also blocks direct removal of a definition from underneath a live parent. If the parent is hard-deleted, the cascade may remove its definition and children; the deferred check sees no surviving parent and succeeds. The checks must not reject ordinary metadata or moderation operations on old unregistered historical rows, but such rows remain quarantined.
3. Add row-local immutability guards for the poll parent type, destination and standard flag/payload shape. Use after-row DEFERRABLE INITIALLY DEFERRED constraint triggers on ballot headers and choices to re-evaluate the affected ballot at commit. An extant header has at least one choice and exactly one choice in single mode. The composite foreign keys ensure choices belong to that poll; a removed ballot under a legitimate cascade does not need a surviving choice. Lock the canonical poll for mutations. Selection mode is immutable after creation under this proposal.
4. Keep old raw Mark SELECT unchanged. Preserve generic text content handling for the four existing types. If poll edits are approved, use the dedicated poll capability; keep the generic content fields null. Existing parent removal and moderation behavior is retained, but any path that previously found targets through raw Mark SELECT needs an explicitly reviewed poll-aware path before it can act on a poll. No blanket moderation or generic RLS broadening.

All new tables are RLS-enabled and have no anon/authenticated direct table, column, or ancillary privileges. Grant only named public RPCs to authenticated and revoke Public/anon. Use explicit bounded SECURITY DEFINER entry points, trusted fixed search paths, and qualified relation references. Keep helpers and tables ungranted. The service worker for protected media/deletion acquires no poll-management role from this change.

## Proposed API

Inputs use SQL UUIDs and arrays. Require a non-null authenticated `auth.uid()` matching `expected_actor_id` for every operation. Never take voter identity, counts, author capability or receipt state from client input. The names below describe the proposed PostgREST functions; parameters can retain the repository's `p_` prefix.

| Operation | Request | Successful response |
|---|---|---|
| `create_poll_mark` | `expected_actor_id, request_id, wall_id, selection_mode, question, options: text[], anonymous: boolean, secret: boolean`. Require `secret=false`; other value or missing flag is invalid. Validate and normalize before writes, retain array order, and keep the exact same request ID for an ambiguous retry. | `{status:"created" or "existing", mark_id, mark_status, poll_revision}`. Existing parent Mark lifecycle decides its status. No create receipt before an atomic commit. Disable Anonymous creation unless and until the proposed UX and privacy behavior are approved. |
| `list_wall_marks_v2` | `expected_actor_id, wall_id, after_pinned, after_created_at, after_mark_id, limit`. Limit 1–20; all cursor fields null for the first page, otherwise all present. | `{status:"available", items:[MarkEnvelope], next_cursor:null or {pinned,created_at,mark_id}}`. Only authorized active rows on that Wall. Sort pinned descending, created_at descending, then ID descending; take one extra authorized row to detect another page. Existing raw Mark SELECT remains the old client path. |
| `get_wall_mark_v2` | `expected_actor_id, wall_id, mark_id`. | `{status:"available", item:MarkEnvelope}` for an exact accessible active row, otherwise the same unavailable response across absent, hidden and inaccessible. Focused Mark links use this path in new capable clients. |
| `read_poll_marks` | `expected_actor_id, wall_id, mark_ids: uuid[]`; nonempty, distinct, at most 20 per call. Callers can chunk a larger Wall page. Optional bounded refresh for Poll snapshots without re-fetching the whole Wall page. Initial focused detail uses get_wall_mark_v2. | `{status:"available", items:[{mark_id, revision, selection_mode, question, options:[{option_id,position,label}], state, capabilities:{can_vote,can_edit,can_close}, ballot:null or {revision,option_ids}, results:null or {ballot_total,counts:[{option_id,count}]} }]}`. Only eligible canonical active polls on the requested Wall appear, in input order. Inaccessible, foreign, hidden, legacy and missing IDs are indistinguishably omitted. Return no identity/selection other than the viewer's authorized ballot. |
| `replace_poll_ballot` | `expected_actor_id, request_id, wall_id, mark_id, expected_poll_revision, expected_ballot_revision, option_ids: uuid[]`. Use zero expected ballot revision for first vote. Reject null, duplicate and cross-poll IDs; require exactly one selection in single mode, and a nonempty valid set in multiple mode. | `{status:"applied" or "existing", mark_id, revision, ballot:{revision,option_ids}}`. Replay of an old successful request must never reapply it after a newer ballot. If it remains authorized, return the current ballot and do not disclose other voters. |
| `close_poll_mark` | If behavior approved, `expected_actor_id, request_id, wall_id, mark_id, expected_poll_revision`. Require server-derived author eligibility and one-way transition. | `{status:"closed" or "existing", mark_id, revision}`. Result visibility remains viewer-scoped. Close increments the poll revision; concurrent stale revisions cannot commit a vote. |
| `edit_poll_mark` | If behavior approved, `expected_actor_id, request_id, wall_id, mark_id, expected_poll_revision, question, options: text[]`. The contract proposes author-only, server-clock Mark edit window, zero prior ballots and open state. | `{status:"updated" or "existing", mark_id, revision}`. Edit increments the revision, making stale option submissions retry via a fresh read. |

Each `MarkEnvelope` is versioned and discriminated by `kind`. For `kind:"mark"`, project only the existing safe Wall-card fields for text/photo/voice/video (their normal mark ID, Wall ID, visibility-appropriate author ID, type, display text/color, Anonymous/Secret flags, rotation, pin, status and creation time). Continue authorized media/author hydration separately and never serialize an underlying row with SELECT *. For `kind:"poll"`, project the same safe parent identity and card metadata and an embedded validated Poll snapshot in the shape used by read_poll_marks. Poll content, counters and choices exist only in that typed snapshot. No raw legacy payload, private author identifier, moderation audit fields or arbitrary vote identity crosses this boundary. The v2 entry points duplicate or reuse the verified legacy viewer predicate for its four existing kinds without relaxing it; check exact behavior with ordinary and blocked users before switching app readers.

**Legacy client isolation.** No change to the raw marks SELECT policy or current legacy subscription; v1 still exposes only the four current kinds. Do not grant poll sidecar table reads or expose poll parent payloads to legacy clients, and prevent poll-specific IDs/content from reaching legacy-compatible generic Alert or realtime projections. When poll notices are approved, carry them only through a tested version-aware route. Initially refresh v2 polls using authorized RPC reads and no new realtime publication. Before rollout, attach an old client and a current V2-capable client to the same private staging fixture: old raw get/list and authenticated realtime receive no poll row; legacy Alerts and focused links do not route to unusable or leaking poll payloads; the new client sees the exact authorized poll once in mixed pinned/unpinned pages. Also verify raw REST behavior with the current owner, accepted member, outsider and approved test roles. A new client flag alone does not prove legacy isolation.

Failure responses are tagged and minimal: `unavailable` for wrong actor, retired/noncanonical parent, missing/inaccessible or no eligible current capability; `invalid` for invalid input; `conflict` for a stale authorized revision; `closed` for voting on an authorized closed poll; `request_id_reused` for different normalized content under an existing same-actor request ID. Only an already authorized resource may return revision/close/conflict details. Normalize transport-layer input rejections and persistence errors in the app service; never expose raw constraint, RLS or subject errors. A client receiving conflict reloads the read surface and preserves the user's unsent choice. A client receiving unavailable drops the stale private result.

### Mutation replay order

Repeat the actor and target gates under lock before returning any receipt. For a currently eligible actor and target, check an existing request receipt before revising or reapplying a state change. A matching committed receipt returns existing with current authorized state, including after a later close if the caller remains authorized to see that state. A different fingerprint returns request_id_reused. For a new request, check closed/editable status and optimistic revisions before writing. An inaccessible or removed target always returns unavailable, including for a previously approved request.

## Authorization, order and moderation

- Creation requires current canonical contribution permissions, which preserve the existing rule against owner self-post on Personal Walls. Neither an open wall nor a Follow alone gives contribution rights. Shared creation uses existing owner/member rules. Persist moderation status by the same parent rules as other Marks.
- Use the same poll-specific viewer rule for V2 mixed history, focused detail and bounded refresh. Leave the v1 rule untouched. Reuse canonical Wall visibility and active account. Propose denying direct interactions with a blocked true poll author even if both users retain group membership; resolve true author privately without returning it. Pending and removed rows do not enter poll voting or normal reads. Existing owner moderation paths operate separately on canonical Mark IDs.
- Vote eligibility within the visible audience is still a Product decision. A candidate predicate requires the approved poll vote policy in addition to active account, exact Wall, active/canonical Mark, membership where applicable, and block checks. Do not accidentally use `can_contribute` as the complete vote policy or grant voting just because someone can view.
- Proposed lock order to validate against existing SQL is poll-only request lock, Wall row, relevant active profiles in stable order when needed, existing pair locks in stable order, parent Mark row, then poll and ballot rows. Take the Wall lock before checking membership and check canonical active status after the Mark lock. Lock the same poll for edit, close and vote. Validate membership, account, moderation and block races in two sessions against existing `0026` operations, the block cleanup triggers and deletion locks. Integration cannot assume this order is safe without evidence.
- All accepted writes and their receipts commit atomically. A stale mutation cannot restore a blocked ballot or change the closed ballot set through voting. For open polls, compute aggregate counts from canonical ballots in the same authorized read snapshot. Apply any approved result-reveal rule on the server; if redacted, return `results:null` with no count data in another field or event. Poll activity must not disclose an Anonymous author or a voter in push, Alert, analytics, share links or realtime projections.
- Hard parent/Wall deletion cascades sidecar and selections. Auth purge removes that account's identifying ballot and receipt records; authored-Mark deletion cascades owned polls. No early deletion is implied. Whether approved closed totals should remain frozen after another account's purge, fall with a live aggregate, or become unavailable requires explicit Product and retention approval. Do not store a retained aggregate or promise frozen totals yet. If an identity-free snapshot is selected, define small-audience handling, retention horizon and erasure/redaction in that review. Also decide how loss of visibility or voting eligibility affects a previously cast ballot. Capture separate before/after purge acceptance evidence. No new vote notification or exposure is part of this contract.

## Migration, deployment and verification order

1. Record protected decisions and establish exact allow/deny policy. Approve in-app limits, voter audience, Anonymous option, result visibility, editing, vote-change and close behavior. If edit/close are not approved, omit those RPCs and report both capabilities false. Freeze privacy and dataset behavior before changing production contracts.
2. Apply a new additive migration in disposable PostgreSQL only after review. Create private tables and constraints first, next the independent deferred poll constraints, versioned actor-bound readers and mutators, and the no-write rollout control default OFF. Keep v1 Mark SELECT and subscriptions on their prior policy. Keep retired row denials and media/storage controls unchanged. Never enable with migration application. Rehearse rollback by disabling new creation/vote/edit/close without deleting data or reviving legacy surfaces. Continued reads must remain subject to original viewer permissions.
3. Add actor-based SQL and two-session regressions. Test direct table denial; generic Mark RPC and retired-kind denial; malformed shapes, same-request exact replay and payload mismatch; one-/multi-choice and two-device stale revisions; cross-poll/wall selections; block and member-removal races; close/edit/Mark removal races; anonymity and one viewer's ballot only; legacy raw/history/detail/Realtime/legacy Alert and link denials; v2 mixed cursor coverage; reciprocal parent/definition checks for owner or definer paths; legacy row quarantine; rejected transactions leave no partial poll/options/votes and purge/foreign-key behavior under the approved retention policy. Verify disabled and approved test enablement paths, migration on empty and upgrade baselines, and executable CI registrations.
4. Implement Frontend integration behind an explicit capability. Use canonical Wall and actor generation when composing or voting. Feed/detail switch together to the versioned contract and fetch bounded snapshots without overfetch. Error states preserve drafts/choices and never invent totals. Submit retry uses the same request ID until a terminal result. Prove raw API, realtime and legacy Alerts/focused links isolate the old installed build before rollout. Keep new poll data absent from unversioned responses; an old client must still render its previous non-poll journeys.
5. Independently review exact schema/API and code before any staging change. On approved isolated staging, prove both Personal and Shared Wall creation/visibility with authorized real users, JWT permission changes and HTTP denial, native iOS/Android offline/retry/accessibility, data handling under normal user permissions, safe disable and recovery. Release owner approves rollout and captures immutable SHA/build/DB evidence. Public release retains other Enhanced Beta gates.

The first safe preparation unit remains the isolated selection validator and its tests. This document does not authorize altering the schema, deploying RPCs, applying migrations, or enabling polls.
